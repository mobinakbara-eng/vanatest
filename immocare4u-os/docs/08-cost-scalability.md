# J. Cost & Scalability Assessment

> **همه‌ی اعداد REQ-VERIFY هستند** — برآوردهای مرتبه‌ی بزرگی برای برنامه‌ریزی، نه قیمت تأییدشده. قبل از تصمیم، صفحه‌ی قیمت هر ارائه‌دهنده را در تاریخ خرید بررسی و تاریخ را ثبت کنید. قیمت Smoobu معمولاً به تعداد واحد بستگی دارد و بزرگ‌ترین هزینه‌ی متغیر نرم‌افزاری است.

## فرض‌های مدل مصرف
* ~۲۵ پیام مهمان + ~۱۰ پیام خودکار به ازای هر رزرو؛ ~۸ رزرو در ماه برای هر واحد.
* LLM: ~۳٬۰۰۰ توکن ورودی + ~۴۰۰ خروجی برای هر پیام ورودی (KB + گفتگو).
* Smoobu API: ~۸ فراخوانی برای هر پیام/رویداد + Reconciliation (هر ۱۵ دقیقه، چند صفحه) — بسیار کمتر از سقف 700/min تا صدها واحد.

|---|---|---|---|---|

## مقیاس‌پذیری — چرا ادعای تئوری نیست
| گلوگاه | آستانه | راهکار طراحی‌شده |
|---|---|---|
| همزمانی Webhook | ده‌ها رویداد در ثانیه | WF-02 فوراً 200 می‌دهد؛ n8n queue mode؛ صندوق ورودی DB |
| Smoobu rate limit | 700 req/min | Reconciliation با صفحه‌بندی و بازه‌ی تاریخ؛ احترام به `Retry-After` |
| تکثیر کار مدیر | REVIEW% × پیام‌ها | KPI نرخ ویرایش؛ تبدیل سؤال‌های تکراری به KB ← AUTO |
| داده‌ی ملک جدید | زمان Onboarding | WF-15 + Template YAML؛ تنظیمات per-property، بدون تغییر منطق |
| شهر جدید | قوانین متفاوت | `cities` + آیتم‌های Compliance پیش‌فرض به تفکیک شهر؛ timezone per property |
| حجم جداول | میلیون‌ها پیام | ایندکس‌ها موجود؛ Partition ماهانه `messages`/`webhook_events` بعد از ~۵M ردیف؛ Retention |

**قاعده‌ی مقیاس:** رفتن از ۱→۱۰ واحد فقط پس از Phase 3 و KPIهای پذیرش؛ ۱۰→۵۰ پس از Phase 7 (Hardening) و تست بار (۱۰× حجم فعلی Webhook).
